## Summary

**Goal:** MacLock updates itself through Sparkle: it checks a signed appcast, offers a
newer release to the user, installs it and relaunches, and the repository carries the
tooling and instructions to publish such a release.

**Oracle:** A build of MacLock at bundle version 1, pointed at a locally served appcast
that the repository's own release script produced for a bundle version 2 build, shows
Sparkle's "A new version is available" alert; after *Install Update* the MacLock process
that comes back is bundle version 2. Observed in the running app, not inferred from
source.

**Misfire:** The updater compiles, links and shows its UI, but the *shipped* Release
build has no usable feed -- a placeholder feed URL, a missing or mismatched EdDSA public
key -- so every real install checks forever and never finds a release. Criterion 2
catches it: the built Release app's Info.plist must carry an https feed URL under this
repository and the exact public key that this Mac's Sparkle signing key prints.

**Constraints:** The app stays unsandboxed, hardened-runtime, Developer ID signed -- no
Sparkle XPC services are needed and none are added. Sparkle's configuration lives in
Info.plist as its documentation asks; runtime code sets nothing but what the user
toggles. The Package.swift / `swift test` arrangement for ProximityCore is untouched:
Sparkle is an app-target dependency only. No new user-facing prompt on first launch --
`SUEnableAutomaticChecks` is set so Sparkle does not ask permission on the second
launch of a menu bar app that has no window to ask from.

**Assumed:**
- Feed URL: `https://github.com/yumaitau/MacLock/releases/latest/download/appcast.xml`
  -- the appcast is uploaded as an asset of each GitHub release, so the URL needs no
  hosting beyond the repository this project already lives in. Changing it later is a
  one-line Info.plist edit.
- An EdDSA key pair is generated on this Mac with Sparkle's `generate_keys`, which
  stores the private key in the login keychain; the public half goes into Info.plist.
  The user's own machine is the signing machine until they say otherwise.
- The update surfaces are a "Check for Updates…" row in the menu bar panel and an
  Updates section in Settings with the automatic-check toggle and the current version.
- Sparkle 2.9.x from Swift Package Manager, pinned `from: "2.9.6"`.
- Verification uses a local HTTP feed on the loopback interface. If App Transport
  Security blocks it, the *test* build alone carries a loopback exception via an
  overridden Info.plist path; the shipped Info.plist gets no ATS exception.

No reference: there is no comparable artifact to sit MacLock's updater beside, and
Sparkle's own behaviour is the standard the criteria name.

## Out of Scope

- Sandboxing, or the Sparkle XPC services that sandboxing needs.
- Delta updates, signed feeds (`SURequireSignedFeed`), release notes hosting, or
  notarisation automation. The script produces the archive and appcast; notarising
  the archive stays a manual step it documents.
- A custom Sparkle user driver -- the standard alerts are used.
- Publishing an actual first release to GitHub.

## Implementation Tasks

### Task 1: Link Sparkle and configure the updater in Info.plist

**Objective:** Add the Sparkle Swift package to the Xcode project, move to a real
`Info.plist` that the generated one merges into, generate the EdDSA key pair and put
the public key, the feed URL and `SUEnableAutomaticChecks` into it, and create the
single updater object the app owns. The Debug and Release builds go green with
`Sparkle.framework` embedded and the signature verifying.

### Task 2: Update surfaces in the panel and Settings

**Objective:** A "Check for Updates…" row in the menu bar panel, enabled only while
Sparkle reports it can check, and an Updates section in Settings with the automatic
check toggle bound to Sparkle's own setting and the current version shown. The toggle
reflects Sparkle's state rather than a parallel flag in `AppSettings`.

### Task 3: Release script that archives the app and generates a signed appcast

**Objective:** `Scripts/generate-appcast.sh` takes a built, signed `MacLock.app` and an
output directory, zips the app with `ditto` (symlinks preserved), runs Sparkle's
`generate_appcast` with the enclosure URL prefix for the GitHub release, and leaves a
zip plus `appcast.xml` ready to upload. It is what Task 4 uses, so the release path
and the tested path are the same path.

### Task 4: Drive an update end to end against a local feed

**Objective:** Build version 1 and version 2, publish version 2 with the script into a
directory served on loopback, launch version 1 pointed at that feed, and take it
through the alert to a relaunched version 2. Then exercise the manual check on an
up-to-date feed and the automatic-check toggle, and settle criteria 1, 3, 4 and 5.

### Task 5: Document updates and the release procedure

**Objective:** Bring the README into line: what MacLock does about updates, where the
controls are, and the exact release steps a future maintainer follows, including that
`CURRENT_PROJECT_VERSION` must increase for Sparkle to see a release.

### Task 6: Gentle reminder for scheduled updates in the panel

**Objective:** Sparkle logs, at error level on every launch, that a background app
scheduling checks without gentle reminders shows alerts users may never notice -- and
for a menu bar app that is true. Adopt `SPUStandardUserDriverDelegate`: let Sparkle
show an update found right after launch in focus, hold the rest, and surface a held
update as an "Update to MacLock x.y…" row in the panel that brings the alert forward.
Added in round 1 after the first live run (4.4).
